📊 1.0 다이어그램 🚀 AI-DLC 2.0 🗺️ 2.0 워크플로우 🧭 2.0 사용자 흐름 🧭 1.0 흐름 🏢 실사례

한 페이지로 보는 실전 AI-DLC 2.0 흐름

사용자가 AI-DLC 2.0 을 0 부터 끝까지 쓸 때 어떤 순서로 무엇을 입력하고, 어떤 Persona-Agent 가 무엇을 산출하며, 어디서 사람의 결정(승인 게이트)이 필요한지를 5 Phase · 32 Stage 단위로 정리합니다.

각 stage 는 ALWAYS / CONDITIONAL 배지로 실행 조건을, SUBAGENT / PER-BOLT / ONCE 로 실행 방식을 표시합니다. 뼈대는 awslabs/aidlc-workflows @ v2 의 컴파일된 stage-graph 기준.

📑 목차

  1. Step 0 — 사전 준비 (harness 설치 · intent)
  2. Step 0.5 — /aidlc 트리거 · scope 자동 compose
  3. Phase 1 — Initialization (3 stage)
  4. Phase 2 — Ideation (7 stage · VG1)
  5. Phase 3 — Inception (8 stage · VG2)
  6. Phase 4 — Construction (7 stage · Bolt · VG3)
  7. Phase 5 — Operation (7 stage · feedback loop)
  8. Cross-cutting — conductor · gate · self-correcting loop
  9. 🎛️ 사용자 조작 knob — scope · depth · test · autonomy
  10. 완료 후 — feedback loop 로 다음 사이클

🗺️ 전체 흐름 한눈에

5 Phase 는 순차 실행되며 phase 경계마다 Verification Gate(traceability 검사)가 있습니다. Construction 은 Unit of Work 단위 Bolt loop 이고, Operation 의 마지막 stage 는 다시 Ideation 으로 feedback loop 를 형성합니다. 실제 실행 stage 는 감지된 scope(9종)에 따라 자동 결정됩니다.

STEP 0 · 사전 준비

BEFORE AI-DLC 2.0 harness 설치 + 만들고 싶은 것(intent) 한 줄
STEP 0.1

🛠️ Harness 설치

REQUIRED
2.0 는 "one core, many harnesses" — 하나의 core 를 도구별로 패키징합니다. bun 런타임과 AWS Bedrock 접근이 필요하며, 최적 성능을 위해 Claude Opus 4.8 이 권장됩니다. 사용하는 도구의 디렉토리를 프로젝트에 복사하면 됩니다.
harness 별 설치 · 호출
  • Claude Code — .claude/ + aidlc/ → /aidlc
  • Kiro IDE / CLI(≥2.6) — .kiro/ + aidlc/ → /aidlc
  • Codex CLI(≥0.139) — .codex/+.agents/+aidlc/ → $aidlc
검증

새 세션에서 /aidlc(또는 $aidlc) 가 인식되면 정상. GA Preview 이므로 known-good 버전 pin 권장.

STEP 0.2

📝 intent 준비 — 무엇을, 왜

권장
1.0 처럼 vision.md 를 미리 완성할 필요는 없습니다. 2.0 은 2.1 Intent Capture stage 가 대화형 명확화 질문으로 의도를 정제하기 때문입니다(원칙 2). 다만 한 문단의 freeform intent 와 (있다면) 팀 표준·제약을 knowledge/ 에 미리 넣어 두면 훨씬 효율적입니다.
준비하면 좋은 것
  • 만들 것 1문단 (무엇 · 누구를 위해 · 왜)
  • 알려진 제약 / no-go-zone
  • 팀 코딩표준·보안규칙 → knowledge/ (C2 후조건으로 hydrate)
High-leverage tip

기계 검증 가능한 규칙(린터·정적분석)을 knowledge/ 에 많이 넣을수록 AI 가 자율 halt 하는 stage 가 늘어 사람 개입이 줄어듭니다.

STEP 0.5

🚀 /aidlc 트리거 · scope 자동 compose

START
freeform intent 와 함께 /aidlc 를 호출하면, 오케스트레이터가 intent 에서 9 scope 중 하나를 자동 감지하거나 Composer 가 EXECUTE/SKIP 그리드를 제안합니다. 사용자가 그리드를 승인하면 32 stage 중 실행할 부분집합이 확정되고 Initialization 이 자동으로 시작됩니다.
User > /aidlc Build a K-beauty recommendation assistant on Amazon Bedrock. Standard depth, ship an MVP first. AI > Detected scope: mvp (22/32 stages). Proposed EXECUTE/SKIP grid: [ ... ] Depth: Standard · Test: Standard. Approve to begin, or /aidlc compose to tailor.
scope 자동 감지 예
  • mvp, poc, bugfix, refactor
  • infra, security-patch, workshop
  • 키워드 없으면 feature(32/32) fallback
사용자 액션

제안된 grid 검토 후 승인. 다르면 /aidlc compose 로 stage 를 직접 조정하거나 --depth/--test-strategy override.

개선 항목을 새 intent 로 → 라이프사이클 순환.

🧷 모든 stage 에 걸친 cross-cutting 동작

아래 항목들은 특정 stage 가 아니라 모든 stage 사이사이에서 일관되게 동작합니다. 2.0 의 점진적 자율성·추적성·중단 안정성을 보장하는 메커니즘입니다.

✋ Human-in-the-loop (여전히 핵심)

2.0 은 HITL 을 없애지 않습니다 — 실행되는 non-bootstrap stage 마다 사람 승인 게이트가 있습니다 (feature = 32 중 29 게이트, poc = 8 중 5). Initialization 3 stage 만 auto-proceed. 방향은 "제거"가 아니라 검증을 기계화해 개입을 점진적으로 줄이는 것입니다.

🚦 Verification Gate ×3

phase 경계에서 자동 traceability 검사: VG1(Ideation→Inception) · VG2(Inception→Construction) · VG3(Construction→Operation). Initialization→Ideation 은 게이트 없이 자동 진행.

🔁 Self-Correcting Loop + Halting

각 stage 는 생성 → 자기검증(C2 후조건) 반복. halting(최대 반복/토큰 예산)에 도달하거나 모호함이 있으면 무한 반복 대신 사람에게 escalate. LLM 판정만 있는 stage 는 자율 halt 불가 → 사람 검증.

📝 68-event 감사 로그

stage 활성·산출·승인·rule 적용 등 모든 결정이 구조적으로 로깅됩니다. 어떤 stage 가 왜, 어떤 순서로 실행됐는지 전부 추적 — 엔터프라이즈 감사 요건 충족.

💾 Session 관리

aidlc-state.md 기반으로 resume(체크포인트 재개) · redo(재실행) · jump(특정 stage 이동) · fresh(새로 시작). 세션이 끊겨도 마지막 미완료 stage 부터 정확히 이어집니다.

🧩 3-Compartment (Generate·Verify·Learn)

모든 stage 는 C1(입력→출력) · C2(post-condition) · C3(런타임 학습) 구조. sensors(required-sections·upstream-coverage, 코드 stage 는 linter+type-check)가 자동 품질 검사.

🌱 Compound Engineering (학습)

사람의 교정·override·escape-hatch 수용이 후조건/guardrail 후보로 제안되고, 승인 시 활성 규칙으로 승격. Practices Discovery(3.2)가 대표 지점 — 실전이 검증 라이브러리를 hydrate.

🚫 숨은 위임 없음

모든 agent 는 disallowedTools: Task — agent 는 서로를 dispatch 하지 않습니다. 오직 conductor 만 stage 를 위임·조율. 실행 순서는 결정적 라우팅.

🎛️ 사용자가 실제로 조작할 수 있는 부분

2.0 에서 사용자가 워크플로우 모양을 직접 조정하는 knob 은 크게 넷 — scope · depth · test-strategy · Construction Autonomy. 앞의 셋은 "무엇을 얼마나", 마지막은 "AI 를 얼마나 풀어줄지" 를 정합니다.

🎚️ Scope — 어떤 stage 를 실행할지

자동 — intent 에서 감지

freeform intent 의 키워드로 9 scope 중 자동 감지 (mvp/poc/bugfix/refactor/infra/security-patch/workshop), 없으면 feature(32/32) fallback. enterprise 는 의도적으로 선택.

조정 — /aidlc compose

제안된 EXECUTE/SKIP 그리드가 맞지 않으면 /aidlc compose 로 Composer 가 stage 를 재구성. 키워드 + 5단어 넘는 설명이 함께면 compose 제안이 자동 발동.

User > /aidlc compose Keep everything but skip market-research and add security-patch's NFR stages.
💡 Tip: scope 는 "어떤 stage 를 돌릴지"만 정합니다. 각 산출물의 상세도는 depth가 따로 결정.

📏 Depth — 산출물 상세도

3 레벨 (독립 축)

Minimal(핵심만, 1–2p) · Standard(완전한 산출물) · Comprehensive(엔터프라이즈 전량 + 컴플라이언스 cross-ref). scope 기본값을 따르되 독립적으로 override 가능.

조정 방법

--depth <level> flag, scope 확정 시점, 또는 아무 승인 게이트에서나 변경.

User > /aidlc --depth comprehensive User > (게이트에서) 이 설계는 minimal 로 줄여줘
⚠️ 주의: depth ≠ scope. depth=minimal 이어도 ALWAYS stage 는 모두 실행됩니다.

🧪 Test Strategy — 테스트 양

3 레벨 (depth 와 별개)

Minimal(Nyquist) — 요구사항당 1 테스트, unit 만, ~5–15개 · Standard(per-component) — 컴포넌트당 5–8, unit+integration · Comprehensive(full) — 컴포넌트당 10–15, 전 유형.

조정 방법

--test-strategy <level>, mid-workflow, 또는 게이트에서. depth 를 따르지만 scope 가 override 가능 (예: workshop = Standard depth + Minimal test).

User > /aidlc --test-strategy comprehensive
💡 Tip: Computational 검증(executable)이 많을수록 AI 가 build-and-test 를 자율 halt 하기 쉬워집니다.

⚡ Construction Autonomy — Bolt 를 얼마나 풀어줄지

Bolt 1 = Walking Skeleton

Construction 의 첫 Bolt 는 항상 게이트·인터랙티브. 뼈대가 도는지 사람이 확인합니다.

한 번의 ladder 프롬프트

walking skeleton 이 통과하면 AI 가 한 번 묻습니다 — "이후 Bolt 를 자율로 진행할까, 매 Bolt 게이트할까?". 답은 Construction Autonomy Mode 로 state 에 저장돼 나머지 Bolt 에 적용.

AI > Walking skeleton shipped & approved. Remaining 6 Bolts: [A] proceed autonomously [B] gate every Bolt User > A
⚡ 병렬: 같은 선행조건을 공유하는 독립 Bolt 들은 parallel batch 로 한 번의 게이트 아래 동시 실행됩니다.
