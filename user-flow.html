STEP 0 · 사전 준비

BEFORE AI-DLC AI 에이전트 설치 + 입력 문서 2 종 작성
STEP 0.1

🛠️ AI 에이전트 환경 준비

REQUIRED
Claude Code · Cursor · Q Developer · Kiro · Amazon Q 중 하나를 설치하고, aidlc-rules 디렉토리를 해당 도구의 룰 경로 (.claude/, .cursor/, .kiro/, .amazonq/ 등) 에 배치합니다. 도구별 인식 경로가 달라도 룰 자체는 동일합니다.
사용자 액션
  • 도구 설치 + 인증
  • awslabs/aidlc-workflows clone
  • 룰 파일을 도구 인식 경로에 복사
검증

도구에서 새 세션 시작 시 welcome-message.md 가 출력되면 룰이 정상 로드된 것.

STEP 0.2

📝 vision.md 작성 — 무엇을 만들 것인가

REQUIRED
Executive Summary · Problem · Target Users · Success Metrics · MVP IN / OUT · Risks 를 채웁니다. Brownfield 의 경우 "Current State" + "무엇은 절대 바꾸지 말 것" 섹션이 추가됩니다. time-pressed 사용자는 example-minimal-vision-*.md 의 minimal 템플릿 사용.
최소 필수 섹션
  • 1 paragraph: what + for whom
  • MVP IN scope 목록
  • MVP OUT scope 목록
  • Open questions (강력 권장)
팁

Open questions 는 Requirements Analysis 의 사전 입력이 됨 — 모호함이 mid-design 단계에서 surprise 되는 걸 막아 줌.

STEP 0.3

⚙️ tech-env.md 작성 — 무슨 도구를 쓸 것인가

REQUIRED
Languages · Frameworks · Cloud Services 의 allow / disallow 리스트, Security/Auth, Testing 정책, 그리고 example code 디렉토리를 제공합니다. tech-env 가 부실하면 AI 가 임의로 라이브러리·패턴을 선택해 의도와 다른 결과가 나옵니다.
prohibited 항목 3 열 표
  • prohibited | reason | use instead
  • reason 없으면 AI 가 대체안 선택을 못 함
High-leverage tip

endpoint · function · test · infra 각 1 개씩의 example code 만 넣어도 코드 일관성이 크게 향상됨.

STEP 0.5

🚀 AI 에이전트 트리거 (워크플로우 시작)

START
준비한 vision.md + tech-env.md 를 가리키며 AI 에게 워크플로우 시작을 지시합니다. AI 는 룰을 로드하고 aidlc-docs/ 디렉토리를 생성한 뒤 audit.md 와 aidlc-state.md 를 초기화합니다.
User > Start AI-DLC. Inputs: - vision.md - tech-env.md Please proceed step by step, ask via question files, and pause for my approval at each gate.

🔵 PHASE 1 · INCEPTION

PLANNING & ARCHITECTURE "무엇을·왜" — 7 stage
STAGE 1.1

🔎 Workspace Detection

ALWAYS
현재 작업 디렉토리가 greenfield (백지) 인지 brownfield (기존 코드) 인지 판별합니다. aidlc-docs/ 산출물이 이미 있다면 stale 여부까지 검사하여 재실행 범위를 결정합니다.
입력
  • 현재 directory tree
  • 기존 aidlc-docs/ (있다면)
산출
  • workspace 분류 (green / brown / resume)
  • stale artifact 목록
사용자 액션

AI 가 제시하는 분류 결과 확인 — 잘못됐다면 정정 입력.

STAGE 1.2

🔍 Reverse Engineering

CONDITIONAL BROWNFIELD ONLY
Brownfield 에서만 실행. 기존 코드를 분석해 9 개 baseline artifact 를 자동 생성합니다. 이 산출물은 이후 Inception · Construction 의 입력으로 재사용됩니다. 상세는 별도 페이지: 🔍 Reverse Engineering 상세.
9 artifact (요약)
  • business-overview.md · architecture.md
  • api-inventory.md · code-structure.md
  • component-inventory.md · technology-stack.md
  • dependencies.md · domain-model.md
  • code-quality-assessment.md
SKIP 조건

Greenfield — 분석 대상 코드가 없으므로 통째로 skip.

사용자 액션

9 artifact review → 잘못된 추정 정정 → Approve.

STAGE 1.3

📋 Requirements Analysis

ALWAYS · adaptive depth
vision.md 와 RE 산출물(있다면)을 입력으로 받아 6 영역 완성도 분석 (Functional / NFR / User Scenarios / Business / Technical / Quality) 을 수행하고, 모호한 영역은 requirement-verification-questions.md 로 사용자에게 질문합니다.
산출 artifact
  • requirement-verification-questions.md
  • requirements.md
사용자 액션 — 질문 응답 패턴

각 질문 아래 [Answer]: A · B · ... · E (Other) 형식으로 답변. 모순 발견 시 추가 round.

Extension 트리거 지점

여기서 security/testing 확장의 opt-in 질문이 자동 삽입됨 (A=enforce / B=skip).

requirement-verification-questions.md ## Question 3: Authentication Should the API enforce authentication for all endpoints? A) Yes — JWT-based, all endpoints B) No — public API, no auth E) Other (describe below) [Answer]: A
STAGE 1.4

👥 User Stories

CONDITIONAL
personas 와 user story 가 product 의도 명확화에 가치 있을 때만 실행. API only · 내부 도구 · 단순 utility 라면 자동 skip.
산출
  • personas.md
  • stories.md
SKIP 조건

사용자 인터랙션 모델이 단순(예: stateless API) 하거나 vision 에 user journey 가 이미 명확.

STAGE 1.5

🗺️ Workflow Planning

ALWAYS
여기까지의 컨텍스트(요구사항 + story + RE) 를 종합해 어떤 stage 를 execute / skip 할지 결정하고, Brownfield 의 경우 transformation scope · cross-package impact 까지 분석합니다. 이후 Construction 의 per-unit loop 계획이 여기서 확정됩니다.
산출
  • workflow-plan.md — 실행할 stage · 순서 · scope
  • (Brownfield) 영향 컴포넌트 맵
사용자 액션

plan 검토 — skip 결정에 동의하지 않으면 정정 입력. plan 승인 후에만 Construction 진입.

STAGE 1.6

🏗️ Application Design

CONDITIONAL
여러 컴포넌트가 협업하는 시스템에서 실행. 컴포넌트 · 책임 · 의존성을 정의하고 mermaid component diagram 을 생성합니다. 단일 컴포넌트 변경이면 skip.
산출
  • application-design.md
  • component-diagram.md
SKIP 조건

단일 component / 명백한 책임 분할 / 변경 영역이 1 파일 수준.

STAGE 1.7

📦 Units Generation

CONDITIONAL
Construction 의 per-unit loop 단위가 될 "unit of work" 들을 정의합니다. 병렬 작업 가능한 의존성 그래프와 함께 산출. DDD aggregate · circular dependency 자동 검출.
산출
  • units.md — 각 unit 의 범위·책임·의존성
사용자 액션

unit 분할 review — 너무 크게 묶이거나 너무 잘게 쪼개졌다면 재분할 요청.

DESIGN · CODE · BUILD & TEST "어떻게" — per-unit loop (4 design + Code Gen) + Build & Test

📐 NFR Requirements

CONDITIONAL PER-UNIT

STAGE 2.5

💻 Code Generation

ALWAYS PER-UNIT

산출

패턴 일관성

STAGE 3

🚀 Operations

PLACEHOLDER
현 시점에서는 placeholder. CI/CD · 모니터링 · 알람 · 운영 런북 자동화가 이 phase 로 확장될 예정. 사용자는 Build & Test 완료 후 자체 배포 파이프라인에 연결합니다.

🧷 모든 stage 에 걸친 cross-cutting 동작

아래 4 가지는 특정 stage 가 아니라 모든 stage 의 사이사이에서 일관되게 동작합니다. 이 메커니즘들이 AI-DLC 의 추적성·재현성·중단 안정성을 보장합니다.

🎯 Human-in-the-loop gate

각 stage 산출 후 "Approve" 응답이 입력될 때까지 다음 stage 로 진행하지 않음. 모순·모호함 발견 시 *-clarification-questions.md 파일이 자동 발행됨.

📝 audit.md 자동 누적

모든 사용자 응답·승인·rule 적용이 ISO 8601 timestamp + append-only 로 기록. 프로젝트 종료 후 그대로 컴플라이언스 evidence 로 활용 가능.

🔁 session-continuity

세션이 중단되었다 재개되면 AI 가 aidlc-state.md + 모든 산출 markdown 을 reload 해 "가장 마지막 미완료 stage" 부터 정확히 이어 진행. 채팅 context loss 영향 없음.

🔌 Extension opt-in 타이밍

로드된 extension 의 .opt-in.md 질문이 Requirements Analysis 의 clarifying questions 에 자동 삽입됨. A=blocking enforce / B=skip 선택은 이후 모든 stage 에 일관 적용.

🎚️ Adaptive depth

depth-levels.md 룰에 따라 각 stage 의 산출 detail 수준(minimal / standard / comprehensive) 이 자동 조정. 사용자가 명시적으로 "더 자세히/간결히" 라고 표현하면 반영.

⚠️ Overconfidence prevention

overconfidence-prevention.md 룰이 AI 의 임의 결정·추측을 차단. 명확치 않은 사항은 추측 대신 질문 발행 으로 처리하도록 강제.

🎛️ 사용자가 실제로 조작할 수 있는 부분

Cross-cutting 항목 중 Extension 과 Adaptive depth 는 사용자가 적극적으로 개입할 수 있는 knob 입니다. 나머지(HITL · audit · session-continuity 등) 가 자동으로 깔리는 기반이라면, 이 둘은 "내가 어떻게 적용할지" 를 선택하는 부분. 구체적으로 어디서·어떻게 조작하는지 정리합니다.

🔌 Extension — 룰을 강제 적용하는 스위치

STEP 1 · 활성화

원하는 extension 의 .md + .opt-in.md 한 쌍을 aidlc-rules/extensions/<도메인>/<이름>/ 경로에 두면 자동 인식. 기본 제공: security/baseline, testing/property-based.

STEP 2 · 응답 — Requirements Analysis 시점

extension 의 .opt-in.md 질문이 clarification-questions 파일에 자동 삽입됨. 사용자는 해당 파일을 열고 [Answer]: 한 글자만 입력하면 됨.

requirement-verification-questions.md ## Question: Security Extensions A) Yes — enforce all SECURITY rules as blocking B) No — skip all SECURITY rules E) Other (describe below) [Answer]: A
STEP 3 · 결과

A 선택 → 이후 모든 단계에서 해당 룰이 blocking constraint. Build & Test 의 SAST 결과·커버리지 임계값이 통과 못 하면 진행 불가.
B 선택 → 룰 비활성. PoC·prototype 에 적합.

STEP 4 · 사내 커스텀 룰 추가

회사 표준이 있다면 같은 패턴으로 직접 만들 수 있음: aidlc-rules/extensions/my-org/coding-style/coding-style.md + coding-style.opt-in.md. 폴더에 두는 것만으로 다음 세션부터 opt-in 질문이 자동 추가됨.

💡 Tip: opt-in 응답은 audit.md 에 함께 기록되어, "이 프로젝트에 어떤 룰이 enforce 됐는가" 를 사후에 항상 추적 가능합니다.

🎚️ Adaptive Depth — 산출물 detail 수준 조정

기본 — 자동 판단

사용자가 별도 표현을 하지 않으면 AI 가 요청 명확도 · 복잡도 · scope · risk · greenfield/brownfield · 사용자 선호 의 6 가지를 종합해 minimal / standard / comprehensive 중 자동 선택.

방법 1 · vision.md 에 의도 명시 (가장 추천)

vision 의 Notes 섹션에 한 줄만 적어 두면 이후 모든 stage 의 detail 수준이 그 방향으로 자동 편향됨.

vision.md ## Notes # minimal 편향 This is a 2-week prototype — keep all artifacts minimal and concise. # 또는 comprehensive 편향 Long-term production system; the docs will serve as ADR. Be comprehensive, include alternatives considered.
방법 2 · 세션 중 자연어로 즉시 조정

특정 산출물이 너무 장황하거나 부족하면 그 stage 의 review 시점에 자연어로 지시. AI 가 해당 산출물을 다시 작성.

User > The requirements.md is too verbose. Please trim it to a minimal version focused on the MVP only. User > The component-diagram.md is too abstract — please add data flow and integration points (comprehensive).
중요 — depth ≠ scope

depth 는 각 산출물의 detail 수준만 조정. "어떤 stage 를 skip 할지" 는 별도로 Workflow Planning 이 결정. depth=minimal 이라도 ALWAYS stage (Workspace Detection · Requirements Analysis · Workflow Planning · Code Generation · Build & Test) 는 모두 실행됨.

⚠️ 주의: "--depth=minimal" 같은 flag 는 없음. 모두 자연어로 의도를 명시하는 방식이며, AI 가 그 의도를 향후 stage 에도 일관 적용합니다.

🔁 완료 후 — 변경이 필요할 때 3-step

구축 완료된 시스템에 변경을 가할 때 AI-DLC 는 자동 cascade 재생성을 하지 않습니다 (의도된 설계 — 자세한 이유는 ✨ 효과 페이지 의 rationale 섹션 참조). 대신 사용자가 다음 3-step 을 명시적으로 트리거합니다.

STEP 1 영향 분석 (no-change) "문서 수정 없이, 이 변경이 어디에 영향을 주는지 알려 줘."
→
STEP 2 설계 update + upstream 확인 "해당 design doc 만 update 하고, requirements / user-stories 도 같이 점검."
→
STEP 3 영향 코드만 regenerate "updated unit X 의 affected files 만 code regeneration."

💡 Standing rule 권장: phase 시작 시 "문서 수정 시마다 requirements / stories 영향 가능성을 매번 알려 줘" 를 박아 두면 누락이 줄어듭니다.
