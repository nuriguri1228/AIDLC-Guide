AI-DLC 1.0 은 "SDLC 를 사람이 개입하는 단계(stage)의 연속으로 실행한다"는 가치를 증명했습니다. 2.0 은 그 방법론(methodology)은 유지하되, 그 위의 워크플로우 계층(workflow layer)을 완전히 재구축하여 점진적 자율 소프트웨어 개발(autonomous software delivery)을 향해 나아갑니다.

핵심은 하나 — 기계로 검증 가능한(machine-checkable) 영역이 넓어질수록 사람의 개입은 줄어든다는 것. 1.0 이 "모든 단계에서 사람의 승인"에 의존했다면, 2.0 은 사람의 판단을 조금씩 기계가 실행 가능한 규칙(post-condition)으로 증류해 AI 가 스스로 검증·교정하는 범위를 점진적으로 넓힙니다.

💡 한 문장 요약: AI-DLC 2.0 = (1.0 의 방법론) + (Skill 단위로 자유 조합되는 building block) + (Generate → Verify → Learn 3-구획 모델) + (스스로 멈출 줄 아는 self-correcting loop) + (하나의 core, 여러 harness).

🧭 2.0 이란 무엇인가 · 왜 다시 지었나

CONTEXT Spec §1 Context & Purpose

AI-DLC(AI-Driven Development Life Cycle)는 요구사항부터 배포까지 사람과 AI 에이전트가 소프트웨어 딜리버리에 어떻게 참여하는지를 구조화합니다. 1.0 은 "SDLC 를 사람이 개입하는 단계의 연속으로 실행"하는 것의 가치를 입증했습니다. 2.0 은 그 방법론을 유지한 채 워크플로우 계층을 다시 지어, 기계로 검증 가능한 영역이 넓어질수록 사람의 개입을 줄여가며 자율 소프트웨어 딜리버리로 진행합니다.

재설계를 이끈 두 가지 힘 (Two forces)

🧱

① 고객이 원한 건 '더 잘게 쪼갠 조립 블록'

실제 고객 사례에서, 팀마다 자기 딜리버리 흐름에 맞게 더 세분화되고(finer-grained) 조합 가능한(composable) building block에 대한 수요가 드러났습니다. 예: 1.0 은 Build & Test를 한 단계로 묶었지만, 거의 모든 고객에게 이건 리뷰·빌드·기능테스트·보안테스트 등 여러 활동이었습니다.

⚙️

② 에이전트 플랫폼이 성숙했다

개별 역량을 패키징하는 Skills, 협업하는 전문가를 모델링하는 멀티에이전트 런타임이 등장해, 그 세분성과 검증 규칙을 steering rule 만이 아니라 네이티브로 표현할 수 있게 됐습니다. 여기에 halting·감사를 위한 결정적 lifecycle hook, 이식 가능한 도구/컨텍스트 전달을 위한 MCP가 도구별 부가 기능으로 얹힙니다.

🎯 2.0 의 지향점: "build me this app" 같은 단발 프롬프트로 intent → 배포까지 한 방에 가는 것은 현실적으로 불가능하다고 봅니다(원칙 6). 대신 단계적 분해(staged decomposition)로 각 단계의 post-condition 을 관리 가능하게 유지하고, 검증 가능한 규칙을 점진적으로 채워(hydrate) 자율성의 범위를 안전하게 넓혀갑니다.

📐 2.0 을 떠받치는 9가지 원칙

PRINCIPLES Spec §2 — 2.0 설계 철학의 핵심

이 9가지 원칙이 2.0 의 모든 설계 결정을 관통합니다. 1.0 과의 차이는 대부분 여기서 비롯됩니다.

1사람의 판단은 기계로 증류할 수 있다

판단·검증·AI 조종에 드는 사람의 노력 상당 부분은, 사람의 결정 패턴을 기계 실행 가능한 형태로 증류하면 줄일 수 있습니다. 이것이 자율 개발로 가는 전제이자 동력. "human-in-the-loop 를 완전히 없앨 수 있는가"에는 합의하지 않되, 모든 단계에서 필요한 사람의 노력을 계속 낮춘다는 데는 정렬합니다.

오늘 AI-DLC 는 모든 단계에서 사람에게 크게 의존 — 이를 '영구 상태'가 아니라 '최적화할 시작 조건'으로 봄.

2모든 intent 는 모호하게 시작한다 (그래도 괜찮다)

모든 비즈니스 intent 는 어느 정도 모호합니다 — 명세 표현의 한계, unknown-unknown, 자연어 자체의 모호성 때문. 따라서 AI 는 가정하지 말고 먼저 명확화 질문(clarifying question)을 던지고 맥락을 모아 intent 를 최대한 풀어낸 뒤 문제를 풉니다.

"매출 대시보드 만들어줘" → 어떤 지표? 어떤 기간? 누구를 위해? → HITL 로 판단/검증 확보.

3AI 는 안전망을 갖춘 자기교정 solver 다

입력·기대출력·건전하고 완전한 post-condition 이 주어지면 AI 는 반복 검증·교정으로 수렴할 수 있습니다. 단 세 조건 — 후조건은 AI 가 못 바꾸는 프로그램으로 검사 가능해야 하고, 성공 기준이 tractable 해야 하며, 반복이 충분히 저렴해야 함. 그리고 모든 loop 는 halting 조건(최대 반복 수 / 토큰 예산)을 반드시 포함 — 못 풀면 무한 반복 대신 사람에게 escalate.

Build & Test, Infra Provisioning 은 자기수렴 가능. Requirements·Design Critique·UI Mockup 은 후조건이 채워질 때까지 사람이 검증.

4Three-Compartment 모델

AI 의 작업을 세 구획으로 표현: C1 "무엇을"(입력·출력·필수 중간 산출물, 선언적) · C2 "맞는지 어떻게 아나"(post-condition = 검증 기준) · C3 "무엇을 배웠나"(런타임 학습 포착). 후조건이 없으면 AI 는 자기교정할 수 없고, 입출력 정의가 없으면 무슨 문제를 푸는지 모릅니다.

전체 후조건(건전성·완전성)은 처음부터 다 있지 않음 → 초기엔 사람 검증이 잦고, C2 를 채워갈수록 자율성이 커짐.

5모든 SDLC 단계가 이 구획 구조에 들어맞는다

이 구획 모델은 코딩·테스트 같은 구현 단계에만 국한되지 않습니다. 요구사항 명확화, 아키텍처 설계, 배포, 모니터링 등 창의적·분석적·기계적 성격을 불문하고 모든 단계를 "정의된 입력 → 기대 출력 (후조건이 관장)"의 변환으로 표현할 수 있습니다.

6단발 압축이 아니라 단계적 분해

intent 에서 배포까지 한 번에 압축하는 건 비현실적 — 두 가지 폭발 때문입니다. ① 후조건 폭발(기능·품질·보안·컴플라이언스·성능·접근성을 한 곳에서 다 검증 = 명세 지옥), ② 조합 탐색 폭발(모든 제약 동시 적용 → 방대한 해공간, 끝나지 않는 loop). 그래서 Skill을 조합의 최소 단위로 도입하고, stage·phase 는 더 유연한 조직 개념으로 둡니다.

1.0 의 정형화된 단계 정의가 "너무 완고(too opinionated)"해 도입 마찰의 원인이었다는 반성에서 출발.

7빅뱅이 아니라 안전한 증분으로 자율화

가드레일·컴플라이언스·보안정책·도메인 제약을 기계 실행 가능하게 증류하는 일은 본질적으로 점진적입니다. ① 가진 것부터 시작(코딩표준·명명규칙 등 이미 아는 후조건) → ② 점진적 hydrate(가드레일을 계속 C2 로) → ③ 안전 증분 크기 확대(후조건 라이브러리가 성숙할수록 한 번에 자율 실행하는 범위가 커짐).

8확장성 (Extensibility)

모든 고객의 가드레일·컴플라이언스·조직 표준을 미리 예측할 수 없으므로 확장성은 기초 설계 제약입니다. 세 가지를 지원 — Additive(baseline 위에 규칙 얹기) · Replacement(특정 규칙 교체·소유) · Composability(같은 3구획 구조로 새 stage 를 저작해 워크플로우에 삽입). 벤더 baseline 과 동일한 보장으로.

9실전에서 배운다 (Compound Engineering)

Skill 은 저작될 때만이 아니라 쓰이면서 개선돼야 합니다. 사람의 수정·재실행·escape-hatch 수용 등 런타임 상호작용을 관찰해 후조건/가드레일 후보로 승격 제안(사람 승인 후 활성). 오늘 한 번 고치고 잊히는 교정이, 2.0 에선 검증 라이브러리를 채우는 피드백 루프가 됩니다.

특정 섹션을 계속 다시 쓰면 → 그 패턴을 새 post-condition 으로 제안. 특정 설계를 반복 override 하면 → guardrail 제안.

🧩 Three-Compartment 모델 — Generate · Verify · Learn

CORE Spec §2 P4 / §3 — 2.0 의 심장부

2.0 에서 모든 stage 정의는 이 3-구획 구조를 따릅니다. 이것이 "AI 가 스스로 검증·교정"을 가능하게 하는 뼈대입니다. 각 구획은 Generate(생성) → Verify(검증) → Learn(학습)에 대응합니다.

COMPARTMENT 1 · GENERATE

무엇을 (The "What")

"무엇이 들어가고 무엇이 나오는가"

입력·출력, 그리고 건너뛰면 품질이 나빠지는 것으로 밝혀진 필수 중간 산출물을 선언. 예: User Stories(입력) → Domain Model(출력). Bounded Context 설계로 가는 길의 event·aggregate·경계 식별을 명령형 지시가 아니라 명시적 추가 출력(선언적)으로 둔다.

COMPARTMENT 2 · VERIFY

맞는지 어떻게 아나

"How Do We Know It's Right"

AI 가 자기 결과를 self-check 하는 post-condition(후조건) — 올바른 출력이 만족해야 할 규칙·제약·품질 검사. 후조건이 없으면 자기교정도 없다. 처음엔 불완전하므로 사람 검증이 잦고, 채워질수록 자율 halting 이 가능.

COMPARTMENT 3 · LEARN

무엇을 배웠나

"What Did We Learn"

런타임 학습 포착 — 관찰된 어떤 신호가 규칙·예시·후조건 후보가 되는지, 그것을 어떻게 C2 나 공용 guardrail 라이브러리로 승격(promotion)할지를 정의. 원칙 9(Compound Engineering)의 기계 장치.

※ 스펙 원문은 이 구조를 대부분 "Three-Compartment Construct"로 부르며, 초기 버전에는 §2 P5 제목에 "Two-Compartment"라는 표기가 남아 있으나 본문 설명은 3구획 기준입니다.

🔁 Self-Correcting Loop 과 검증의 두 종류

VERIFY Spec §3 Generate-Verify-Learn

자기교정 loop 의 실제 흐름 — 명확화 → 계획 → 실행 → 자기검증 반복 → (수렴 or halting) → 필요시 escalate.

STEP 1
명확화 판단

이 stage 실행에 사람의 추가 설명이 필요한지 AI 가 스스로 평가하고, 모호하면 사람에게 clarify 요청.

STEP 2
계획 생성 · 실행

plan 을 세우고 그에 따라 task 를 실행해 출력을 생성(Generate).

STEP 3
자기검증 반복

C2 후조건이 충족될 때까지 self-verification loop 를 반복(Verify).

STEP 4
halting / escalate

반복·토큰 한도 도달 시 무한 반복 대신 중단하고, 못 풀었으면 사람에게 escalate.

C2 후조건은 두 종류 — 이 구분이 "언제 AI 가 혼자 멈춰도 되는가"를 결정합니다.

🧠 Inferential Verification (추론적 검증)

LLM instruction 으로 표현 · 비(非) binary

정오(pass/fail)가 딱 떨어지지 않는 후조건에 적합. 대부분의 코드 리뷰 규칙처럼 뉘앙스를 살펴야 하는 품질 heuristic.

단, 같은 모델이 생성하고 자기가 자연어 후조건 충족 여부를 판단하면 "글자만 만족"할 위험이 있습니다. 그래서 C2 가 LLM 판정만으로 이뤄진 stage 는 스스로 halt 하지 않고 사람 검증을 받습니다.

⚠️ 자율 halt 불가 → 사람 검증 필수

⚙️ Computational Verification (계산적 검증)

Executable(스크립트·툴·커스텀 코드)로 표현 · 결정적

모호함·확률적 판단에 무관용, 결정적으로 강제해야 하는 후조건에 적합. 예: "프로덕션에서 CloudFormation 스택을 삭제하는 코드 경로 없음", "인증 없이 노출되는 API 엔드포인트 없음" 같은 no-go-zone.

이런 규칙은 LLM 해석이 아니라 커스텀 린터·정적분석으로 검증. 결정적으로 검증되므로 이 비중이 커질수록 사람 개입 없이 자율 halt 가능한 stage 가 늘어납니다.

✅ 자율 halt 가능 → 자율성 확대의 열쇠

🏗️ 새 구조 — 5개의 building block

STRUCTURE Spec §3 — DRY · 관심사 분리 · 도구 네이티브 최대 활용

2.0 은 세 가지 best practice(DRY, 관심사 분리, 도구별 네이티브 기능의 최대 활용)를 기반으로 다음 5개 구성요소로 재조직됩니다.

🤝

① Persona-Agent 라이브러리

사람 팀이 전문가로 구성되듯, 협업 역학을 모델링하는 AI-네이티브 에이전트들. 각자 집중된 전문성을 가지고 공유 목표를 향해 멀티에이전트 워크플로우로 협업.

📚

② Stage 라이브러리

각 stage 는 "어떤 작업을 해야 하고, 끝났을 때 어떤 산출물이 존재해야 하는가"를 정의. (3-구획 구조로 저작)

🧠

③ Knowledge 라이브러리

에이전트가 자기 출력을 생성·자기교정할 때 사용하는 지식. (구현체에선 방법론 지식 / 팀 지식의 2-tier 로 분리)

🎼

④ Orchestrator 정의

AI 를 사용해 stage 들을 적응형(adaptive) 워크플로우로 조합하고 실행을 추적·관리. (다음 섹션 상세)

📦

⑤ Package Manager

위 정의들을 도구별 아티팩트(Kiro·Claude Code subagent/skill 등)로 패키징 — 각 플랫폼 고유 장점을 살려서.

📦 Package Manager 의 DRY 원칙: 각 stage 는 단일 정본(canonical) 정의 파일로 유지되고, 도구별 구현은 내용을 복사하지 않고 파일명 참조로 가리킵니다. 공유 정의는 stage 구조 · C1/C2 계약 · orchestrator hint · cross-stage 후조건 라이브러리를 다루되, Claude Code 의 skill-scoped hook, Cursor 의 다중파일 편집, Copilot 의 PR-native loop, Kiro 의 spec-kit diff 같은 도구 고유 기능은 각 emitter 가 그 위에 얹습니다. → "최소공통분모"로 깎이지 않으면서 이식성 유지.

🎼 Orchestrator(Conductor)의 5가지 역할

ORCHESTRATION Spec §4 — 워크플로우의 제어 평면

Orchestrator 는 Skill(stage)들을 일관된 end-to-end 개발 흐름으로 조합·순서화·모니터·적응시킵니다. 각 stage 의 선언 메타데이터(C1 입출력, stage 목적, orchestrator hint)를 근거로 워크플로우를 조립합니다.

aGoal Ownership

end-to-end 목표를 스스로 소유하고 선언된 성과 전달에 책임을 짐. 개별 stage 에 목표 추적을 위임하지 않고 macro view 를 유지, 전체 출력이 원래 intent 를 만족하는지 보장.

bWorkflow Composition

discrete stage 들을 적응형 워크플로우로 조립. intent 성격(greenfield vs 버그픽스/리팩터), 가용 컨텍스트 (문서 이미 충분하면 해당 stage 생략·축약), 런타임 신호, 고객 저작 stage(hint)에 따라 결정. 고정 파이프라인이 아니라 가변(mutable) plan을 유지하며 실행 중 적응.

cRouting · Observability · Control

운영 제어 평면. 올바른 입력으로 stage 트리거, 실행 상태 추적, halting 조건 강제, 수렴 실패 시 escalation 관리 (일시정지→사람 노출→해결 후 재개), 그리고 모든 결정의 감사 추적(audit trail) 유지 — 어떤 stage 가 왜, 어떤 순서로 활성됐는지.

dAbstraction Boundary

각 stage 를 블랙박스로 취급. 내부 동작에 간섭하지 않고 완료 시 선언된 후조건 충족만 검증. → 모듈성 보존, stage 들이 독립적으로 진화 가능.

eCross-Stage Invariants

모든 후조건이 단일 stage 소유는 아님. 명명 규칙·보안 정책·문서 표준처럼 워크플로우 전체를 가로지르는 불변식을 적절한 체크포인트에서 평가하고 전역 제약으로 강제.

🛣️ 도입 로드맵 — 안전한 증분 자율성

ADOPTION Spec §2 P7 — 빅뱅이 아니라 점진적으로

완전 자율은 하루아침에 오지 않습니다. 조직의 가드레일·컴플라이언스·보안정책·도메인 제약을 기계 실행 가능하게 증류하는 일은 본질적으로 점진적입니다. 2.0 은 이를 블로커가 아니라 기대되는 도입 경로로 받아들입니다.

STEP 1

가진 것부터 시작

이미 알고 코드화할 수 있는 후조건(코딩표준·명명규칙·기본 보안규칙)부터 정의. AI 는 그 경계 안에서 자율 실행하고, 나머지는 사람에게 escalate.

STEP 2

점진적 hydrate

시간이 지나며 가드레일·컴플라이언스·도메인 규칙을 점차 C2 정의로 증류. 추가할 때마다 AI 가 자율 검증·자기교정할 수 있는 경계가 넓어지고 그 단계의 사람 개입 필요가 줄어듦.

STEP 3

안전 증분 크기 확대

후조건 라이브러리가 성숙할수록 한 번에 안전하게 자율 실행하는 범위가 커짐. 예전엔 매 스텝 사람 판단이 필요하던 것이, 이제 여러 stage 를 자율로 통과.

📋 구현 가이드라인 8원칙

GUIDELINES Spec §6 Implementation Guidelines
1. 결정적 라우팅

stage 순서와 워크플로우 전환은 orchestration 계층이 결정.

2. 에이전트 특화

도메인 판단은 적절한 전문가 persona 에 위임.

3. 산출물 추적성

각 stage 가 무엇을 소비·생산하는지 선언.

4. 사람 승인

non-bootstrap stage 는 명시적 승인 필요.

5. 도구 소유 상태

상태·감사 전환은 기계적으로 처리.

6. 자문적 검증

검증은 품질 결정과 감사 가능성을 뒷받침.

7. 통제된 학습

새 규칙은 조용히가 아니라 의도적으로 승인·편입.

8. 숨은 위임 금지

에이전트는 재귀적으로 다른 에이전트를 생성하지 않음 — conductor 가 조율.

🧵 정리하자면 — AI-DLC 2.0 은 1.0 의 "구조화된 방법론 + 인간 통제"라는 핵심 가치를 버리지 않습니다. 대신 그 위에 Skill 단위의 조합성, 기계 검증 가능한 후조건, 스스로 멈출 줄 아는 자기교정 loop, 실전에서 배우는 학습 루프, 그리고 하나의 core 에서 여러 도구로 퍼지는 배포 모델을 얹어, "사람이 통제하되 점점 덜 개입하는" 자율 개발로 한 걸음씩 나아가도록 다시 설계된 버전입니다.
