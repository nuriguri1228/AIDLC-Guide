STEP 0 · 사전 준비 (초기 세팅)

BEFORE AI-DLC 2.0 native aidlc 설치 · harness config · provider — 1.0 대비 변경 (v2.8.0 부터 native 배포)
한눈에

⚖️ 1.0 vs 2.0 — 초기 세팅이 이렇게 달라졌다

1.0 은 순수 마크다운 룰 묶음이라 "복사해서 붙이면 끝"이었습니다. 2.0 은 실행되는 엔진 (결정적 엔진·훅·CLI 툴 + 멀티에이전트 런타임 + lifecycle hook)을 갖기 때문에, 룰 복사 대신 엔진 런타임 설치 → 프로젝트에 harness 구성 → doctor 점검 순서가 필요합니다. v2.8.0 부터는 native aidlc 명령이 전 harness 런타임을 함께 설치하므로 Bun·Node.js 가 필요 없습니다.
AI-DLC 1.0 설치
  • 순수 .md steering rule 묶음
  • 룰을 도구 경로(.claude/·.cursor/·.amazonq/…)에 복사
  • 런타임·빌드·클라우드 불필요
  • 모델·도구·벤더 무관 (any IDE / any model)
  • 트리거: 채팅에 "Using AI-DLC, …"
AI-DLC 2.0 설치 — 새로 필요한 것
  • native aidlc 명령 설치 (install.sh / install.ps1) — Bun·Node.js 불필요
  • 프로젝트 루트에서 aidlc config --harness <name> — harness 런타임 + aidlc/ 작업공간 생성
  • aidlc doctor 헬스체크 + harness 별 trust/hook 승인
  • 모델 provider 는 harness 가 이미 쓰는 것 유지 (Bedrock 은 선택 사항)
  • 트리거: /aidlc <intent> (Codex 는 $aidlc)
STEP 0.1

🧩 AI-DLC 설치 — native aidlc 명령

REQUIRED
README Quick Start 의 설치 스크립트가 native aidlc 명령과 모든 harness 런타임을 설치합니다(체크섬 검증 포함). 셸에서 aidlc 를 못 찾으면 설치기가 출력한 PATH 안내를 적용하거나 새 셸을 여세요.
# macOS / Linux / WSL curl -fsSL https://github.com/awslabs/aidlc-workflows/releases/latest/download/install.sh | sh # Windows PowerShell irm https://github.com/awslabs/aidlc-workflows/releases/latest/download/install.ps1 | iex # 이후 업데이트 (머신 런타임) — 프로젝트는 워크플로우 사이에 aidlc config 로 refresh aidlc update
대안 — Bun 기반 manual copy

native 실행 파일을 설치할 수 없거나 프로젝트 파일을 직접 관리하려면 Bun 을 설치하고, 릴리스의 aidlc-copy-runtime-X.Y.Z.tar.gz 를 받아 runtime/<harness>/ 디렉토리 전체를 프로젝트에 복사합니다. 이 경로는 native aidlc 명령이 필요 없습니다(대신 Bun 필요).

모델 권장

현재 권장 모델은 Claude Opus 4.8 입니다. 약한 모델에선 conductor 가 선택적 stage 스텝(reviewer pass·learnings 의례)을 건너뛰거나 승인 게이트를 서두를 수 있습니다. 배포된 프로젝트 설정은 provider·모델을 고정(pin)하지 않고 사용자가 고른 것을 그대로 씁니다.

STEP 0.2

❓ AWS Bedrock 이 꼭 필요한가?

핵심 질문
결론 — 필요 없습니다. 방법론과 배포본은 provider 독립적입니다. README 는 "Model-provider setup belongs to the harness. Shipped project configuration keeps the provider and model already selected by the user … The methodology itself is provider-independent." 라고 명시합니다. Getting Started 도 Claude Code · Codex · opencode 배포본이 사용자가 이미 설정한 provider 를 보존하고 "Amazon Bedrock is an explicit option" 이라고 설명합니다. v2.10.0 CHANGELOG: "configuration keeps the current provider unless Amazon Bedrock is explicitly selected."
harness 별 provider
  • Claude Code — Claude Code 가 지원하는 provider 중 사용 중인 것 그대로 (Bedrock 은 명시 선택 시에만). 다른 provider 는 aidlc config providers --provider other --yes 로 기록
  • Kiro CLI / Kiro IDE — provider 설정 불필요 (모델 접근이 Kiro 에 포함, v2.9.0~)
  • Codex CLI — ~/.codex/config.toml 의 provider·모델 상속
  • opencode — 세션 provider 를 전역 설정
  • Cursor — IDE/CLI 로그인 · GitHub Copilot — GitHub 로그인 또는 BYOK
Bedrock 을 쓰고 싶다면 (선택)

aidlc config providers 에서 amazon-bedrock 선택(또는 Claude Code 에서 직접 설정) → Bedrock 모델 카탈로그에서 모델 접근 enable → aws configure / aws sso login 등 표준 자격증명 체인 → 모델이 있는 리전 사용. 현재 provider 를 유지하려면 keep current(--provider current).

Bedrock 을 선택했는데 실패할 때

README Troubleshooting: "Bedrock access fails → Enable the configured models and verify AWS credentials and region". 자격증명·개인 override 는 공유 .claude/settings.json 이 아니라 .claude/settings.local.json 이나 AWS 자격증명 파일에 두세요.

Kiro 사용자 참고

Kiro(IDE/CLI)에서 Opus 4.8 을 쓰려면 유료 Kiro 플랜이 필요합니다.

이전 버전 참고: 이 페이지의 이전 판(v2 GA Preview 기준)은 "배포본 모델 설정이 Bedrock 에 고정돼 사실상 필요하다"고 안내했습니다. 현재 main(v2.10.0)에는 해당되지 않습니다.

STEP 0.3

🛠️ Harness 선택 · config · doctor

REQUIRED
"one core, many harnesses" — 방법론은 harness-neutral core/ 에 한 번 정의되고 7개 harness (Claude Code · Kiro CLI ≥2.6 · Kiro IDE · Codex CLI ≥0.145.0 · Cursor · opencode ≥1.17 · GitHub Copilot CLI ≥1.0.74 / VS Code ≥1.130)에서 동일하게 동작합니다. 프로젝트 루트에서 aidlc config --harness <name> 이 harness 런타임과 aidlc/ 작업공간을 만들고 소유권 baseline 을 기록합니다 (--dry-run 으로 미리보기, harness 없이 실행하면 대화형 설정).
# 프로젝트 루트에서 cd /path/to/your-project aidlc config --harness claude # kiro · kiro-ide · codex · cursor · opencode · copilot aidlc doctor # harness 를 열고 호출 claude # Kiro CLI: kiro-cli chat · Codex: codex · opencode: opencode · Cursor: IDE 또는 agent /aidlc Build a REST API for inventory management
호출 방법 · config 후 할 일
  • Codex CLI 만 $aidlc (또는 /skills → aidlc), 나머지는 /aidlc
  • Claude Code — /hooks 에서 프로젝트 훅 승인 후 재시작
  • Copilot — 프로젝트 폴더 trust · Kiro/Cursor/opencode — 프로젝트 열기
  • 완료 후 aidlc doctor 로 런타임·provider·hook·trust·state 점검
⚠️ Codex — git 저장소 + hook trust 필수

Codex 는 git 저장소 안에서만 프로젝트 .codex/hooks.json 을 찾고, trust 하지 않은 훅은 실행하지 않습니다. codex 실행 후 hooks 대화상자에서 "Trust all and continue" 를 고르거나, 생성된 .codex/trust-seed.toml 의 <PROJECT_DIR> 를 절대경로로 바꿔 $CODEX_HOME/config.toml 에 병합하세요.

여러 harness 공존 (v2.10.0)

엔진 디렉토리가 겹치지 않는 harness 들은 한 프로젝트에 함께 구성할 수 있습니다. Kiro·Codex·Cursor·opencode 는 harness-neutral 공유 AGENTS.md 블록을 쓰고 native 설정은 각자 파일에 둡니다. Claude Code 는 어떤 harness 와도 공존 가능. 단 Kiro CLI↔Kiro IDE(.kiro/ 공유), opencode↔Copilot(.aidlc/ 공유)은 불가하고 Copilot 의 AGENTS.md 블록은 배타적입니다.

업데이트 흐름

aidlc update 는 머신 런타임만 갱신합니다. 각 프로젝트는 워크플로우가 끝난 뒤 aidlc doctor → aidlc config 로 refresh (진행 중인 워크플로우가 있으면 refresh 거부). 플러그인을 쓰면 이후 /aidlc plugin sync.

STEP 0.4

📚 knowledge 준비 + intent 한 줄

권장
1.0 처럼 vision.md/tech-env.md 를 미리 완성할 필요는 없습니다 — 2.0 은 1.1 Intent Capture(또는 Ideation 을 건너뛰는 scope 에선 2.3 Requirements Analysis)가 대화형 명확화로 의도를 정제합니다(원칙 2). 대신 2.0 은 two-tier knowledge — 방법론 지식(프레임워크 제공)과 팀 지식(사용자 관리)을 분리합니다. 팀 표준·제약을 aidlc/knowledge/(= aidlc/spaces/<space>/knowledge/)에 넣어 둘수록 AI 의 자율 범위가 커집니다.
준비하면 좋은 것
  • 만들 것 1문단 (무엇 · 누구를 위해 · 왜)
  • 알려진 제약 / no-go-zone
  • 팀 코딩표준·보안규칙 → aidlc/knowledge/ (C2 후조건으로 hydrate)
High-leverage tip

기계 검증 가능한 규칙(린터·정적분석·executable 후조건)을 aidlc/knowledge/ 에 많이 넣을수록 AI 가 자율 halt 하는 stage 가 늘어 사람 개입이 줄어듭니다 — 2.0 이 말하는 "안전한 증분 자율화" 의 출발점입니다.

STEP 0.5

🚀 /aidlc 트리거 · scope 자동 compose

START
/aidlc <profile> 로 11 scope(workflow profile) 중 하나를 직접 고르면 즉시 시작하고 stage·게이트 수를 출력합니다. freeform intent 만 주면 키워드로 scope 를 제안(확인 필요)하거나, 풍부하거나 모호한 설명이면 Composer 제안(compose offer)으로 EXECUTE/SKIP 그리드를 받습니다. 승인하면 33 stage 중 실행할 부분집합이 확정되고 Initialization 이 자동으로 시작됩니다.
User > /aidlc Build a K-beauty recommendation assistant on Amazon Bedrock. Standard depth, ship an MVP first. AI > Starting a "mvp" workflow for: "Build a K-beauty ..." - N of 33 stages, N approval gates. Confirm to proceed, name a different scope, or say "compose" for a tailored plan. # mvp 의 정적 route 는 23/33 · Standard depth · Standard test. # 실제 stage·게이트 수(N)는 compiled grid 와 workspace scan 으로 계산돼 표시됩니다 # (예: greenfield 면 Reverse Engineering 제외).
scope 자동 감지 예
  • mvp(23/33), poc(8), bugfix(9), refactor(10)
  • infra(13), security-patch(10), workshop(26), express(10)
  • 키워드가 없으면 엔진 기본값은 classic(18/33) — 대화형 시작에선 compose offer 가 먼저 뜰 수 있음. 예전 기본값(feature)을 원하면 AWS_AIDLC_DEFAULT_SCOPE=feature
  • feature·enterprise(33/33)는 명시적으로 선택
사용자 액션

제안된 scope/grid 검토 후 승인. 다르면 다른 scope 이름을 대거나 /aidlc compose 로 stage 를 조정하고, 필요하면 --depth/--test-strategy/--review override.

🧷 모든 stage 에 걸친 cross-cutting 동작

아래 항목들은 특정 stage 가 아니라 모든 stage 사이사이에서 일관되게 동작합니다. 2.0 의 점진적 자율성·추적성·중단 안정성을 보장하는 메커니즘입니다.

✋ Human-in-the-loop (여전히 핵심)

2.0 은 HITL 을 없애지 않습니다 — 실행되는 non-bootstrap stage 마다 사람 승인 게이트가 있습니다 (문서 기준 feature = 33 stage · 29 게이트). 시작 시 확인 문구가 compiled grid·workspace scan 으로 계산한 stage·게이트 수를 먼저 보여줍니다. Initialization 3 stage 만 auto-proceed. 방향은 "제거"가 아니라 검증을 기계화해 개입을 점진적으로 줄이는 것입니다.

🚦 Verification Gate ×3

phase 경계에서 자동 traceability 검사: VG1(Ideation→Inception) · VG2(Inception→Construction) · VG3(Construction→Operation). Initialization→Ideation 은 게이트 없이 자동 진행.

🔁 Self-Correcting Loop + Halting

각 stage 는 생성 → 자기검증(C2 후조건) 반복. halting(최대 반복/토큰 예산)에 도달하거나 모호함이 있으면 무한 반복 대신 사람에게 escalate. LLM 판정만 있는 stage 는 자율 halt 불가 → 사람 검증.

📝 105-event 감사 로그

stage 활성·산출·승인·rule 적용 등 모든 결정이 105 종 이벤트로 구조적으로 로깅됩니다. intent 의 audit/ 에 clone 별 shard(<host>-<clone>.md)로 append-only 기록되어 동시 작업에도 git 충돌이 없습니다. aidlc attest resolve 는 커밋/diff 를 리뷰된 Unit 에 매핑해 verified·drifted·unattested 등으로 판정합니다(commit provenance, v2.9.0).

💾 Session 관리

aidlc-state.md 기반으로 resume(체크포인트 재개) · redo(재실행) · jump(특정 stage 이동) · fresh(새 intent 병행). 세션이 끊겨도 마지막 미완료 stage 부터 정확히 이어집니다(/aidlc --resume). 끝내지 않을 intent 는 /aidlc intent archive <name> 로 record·감사 기록을 지우지 않고 보관(unarchive 로 복원, v2.9.0).

🧩 3-Compartment (Generate·Verify·Learn)

모든 stage 는 C1(입력→출력) · C2(post-condition) · C3(런타임 학습) 구조. sensors(required-sections·upstream-coverage, 코드 stage 는 linter+type-check)가 자동 품질 검사.

🌱 Compound Engineering (학습)

사람의 교정·override·escape-hatch 수용이 후조건/guardrail 후보로 제안되고, 승인 시 활성 규칙으로 승격. Practices Discovery(2.2)가 대표 지점 — 실전이 검증 라이브러리를 hydrate.

🚫 숨은 위임 없음

Claude Code 에선 모든 agent 가 disallowedTools: Task(다른 harness 는 native tool policy 로 동일 경계) — agent 는 서로를 dispatch 하지 않습니다. inline·subagent·pipeline·mob 어느 topology 든 오직 conductor 만 위임·조율 (14 agent = 도메인 11 + reviewer 2 + composer). 실행 순서는 결정적 라우팅.

🎛️ 사용자가 실제로 조작할 수 있는 부분

2.0 에서 사용자가 워크플로우 모양을 직접 조정하는 knob 은 크게 넷 — scope · depth · test-strategy · Construction Autonomy. 앞의 셋은 "무엇을 얼마나", 마지막은 "AI 를 얼마나 풀어줄지" 를 정합니다. 여기에 review cap(--review adversarial|advisory|none — 낮추기만 가능)과 Guard Policy가 더해집니다.

🎚️ Scope — 어떤 stage 를 실행할지

자동 — intent 에서 감지

11 scope — 키워드로 자동 제안 (mvp/poc/bugfix/refactor/infra/security-patch/workshop/express), 키워드가 없으면 엔진 기본값 classic(18/33 · v1 스타일 Inception+Construction, Build and Test 까지) — 풍부한 설명은 compose offer 로. feature·enterprise(33/33)는 의도적으로 선택. 예전 기본값 복원: AWS_AIDLC_DEFAULT_SCOPE=feature.

조정 — /aidlc compose

제안된 EXECUTE/SKIP 그리드가 맞지 않으면 /aidlc compose 로 Composer 가 stage 를 재구성. 5단어가 넘는 설명은 보통 compose offer 를 받습니다(단 refactor·mvp·poc·CVE 등 명확한 키워드는 해당 scope 제안). 진행 중에는 PENDING stage 만 재구성(recompose)됩니다.

User > /aidlc compose Keep everything but skip market-research and add security-patch's NFR stages.
💡 Tip: scope 는 "어떤 stage 를 돌릴지"만 정합니다. 각 산출물의 상세도는 depth가 따로 결정.
🛡️ Guard Policy (구 Change Control): strict · relaxed · off — 승인한 것이 바뀌었을 때 다시 승인을 받을지(strict), 감사 행(CHANGE_ACCEPTED)만 남기고 계속할지(relaxed/off)를 정합니다. 기본값은 enterprise·security-patch·infra 가 strict, 나머지는 relaxed. /aidlc --guard-policy relaxed 로 변경, memory 의 Mode: strict 가 우선합니다.

📏 Depth — 산출물 상세도

3 레벨 (독립 축)

Minimal(핵심만, 1–2p) · Standard(완전한 산출물) · Comprehensive(엔터프라이즈 전량 + 컴플라이언스 cross-ref). scope 기본값을 따르되 독립적으로 override 가능.

조정 방법

--depth <level> flag, scope 확정 시점, 또는 아무 승인 게이트에서나 변경.

User > /aidlc --depth comprehensive User > (게이트에서) 이 설계는 minimal 로 줄여줘
⚠️ 주의: depth ≠ scope. depth=minimal 이어도 ALWAYS stage 는 모두 실행됩니다.

🧪 Test Strategy — 테스트 양

3 레벨 (depth 와 별개)

Minimal(Nyquist) — 요구사항당 1 테스트, unit 만, ~5–15개 · Standard(per-component) — 컴포넌트당 5–8, unit+integration · Comprehensive(full) — 컴포넌트당 10–15, 전 유형.

조정 방법

--test-strategy <level>, mid-workflow, 또는 게이트에서. depth 를 따르지만 scope 가 override 가능 (예: workshop = Standard depth + Minimal test).

User > /aidlc --test-strategy comprehensive
💡 Tip: Computational 검증(executable)이 많을수록 AI 가 build-and-test 를 자율 halt 하기 쉬워집니다.

⚡ Construction Autonomy — Unit checkpoint 를 얼마나 풀어줄지

첫 Unit = Walking Skeleton (skeleton-on)

첫 DAG Unit 은 실제 통합 검사를 통과한 뒤 항상 사람이 승인합니다. 뼈대가 진짜 도는지 확인하는 지점입니다.

한 번의 autonomy 제안

skeleton-on 이면 skeleton checkpoint 이후, skeleton-off 면 Construction 진입 시 한 번 묻습니다 — Continue automatically / Review each checkpoint. 답은 Construction Autonomy Mode(autonomous/gated)로 저장되고 다시 묻지 않습니다.

AI > Skeleton verified with <verification_command> (exit 0) and approved. [1] Continue automatically [2] Review each checkpoint User > 1
on-demand 변경 (v2.9.0)

Construction 중 언제든 자율을 허용/회수할 수 있습니다(aidlc engine bolt set-autonomy --mode autonomous|gated, 허용은 새 사람 턴 필요). autonomy 는 일반 checkpoint 승인만 대신합니다 — Plan Approval·검증 명령 선택·skeleton 승인·실패 대응은 여전히 사람.

⚡ 병렬: 기본(unit-major)은 직렬입니다. 병렬로 돌리려면 stage-major + Construction Execution: swarm 을 명시적으로 선택 — 의존성이 풀린 Unit 들이 batch 로 함께 빌드되고, batch checkpoint 에서 한 번에 승인(또는 자동)됩니다.
